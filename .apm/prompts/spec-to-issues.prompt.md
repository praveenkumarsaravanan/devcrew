# Spec to Issues — Decompose a Spec into Tracker Tasks

Break down a `.spec.md` specification file into parallelizable tasks and create them in the configured task tracker.

## Steps

1. **Identify the spec file:**
   - If the user provides a path, use that.
   - If not, look for `.spec.md` files in the project root or `specs/` directory.
   - If multiple specs exist, ask the user which one to decompose.

2. **Analyze the specification:**
   - Read all requirements (REQ-IDs) from the spec.
   - Identify independent, non-overlapping components.
   - Map dependencies between components (which must complete before others can start).
   - Estimate relative size for each component (S / M / L).

3. **Generate the task breakdown:**
   For each component, produce:
   - **Title:** Concise, action-oriented (e.g., "Implement user authentication endpoint")
   - **Description:** References the relevant spec section and REQ-IDs
   - **Acceptance criteria:** Derived from the spec's requirements
   - **Dependencies:** Which other tasks must complete first
   - **Labels:** Component type (api, ui, service, migration, test, docs)
   - **Size estimate:** S / M / L

4. **Present the breakdown for review.** Show the task list with dependency graph before creating anything.

5. **Create tasks in the configured tracker:**

   Read the tracker from `.project-context.md`:

   | Tracker | Action |
   |---------|--------|
   | `jira` | Create Epic + child Stories/Tasks using the Atlassian MCP. Use the stored project key. |
   | `github-issues` | Create parent issue with task list + child issues with labels and milestone using the GitHub MCP. |
   | `linear` | Create project + child issues using the Linear MCP. |
   | `none` | Output a Markdown task list with checkboxes that the user can copy. |

6. **Present the created tasks** with links and confirm completion.

## Dependency Visualization

Before creating tasks, present a dependency diagram:

```
[Task A] ──→ [Task C] ──→ [Task E]
[Task B] ──→ [Task D] ──↗
```

Tasks without dependencies can be worked in parallel.

## Notes

- This prompt works with any `.spec.md` file — whether generated by `spec-templates` or written manually.
- The task breakdown respects the spec's requirement IDs for traceability.
- If the spec is incomplete (missing acceptance criteria or unclear requirements), flag the gaps before creating tasks.
- Each created task references back to the original spec file for context.
